Technical Reference

lex-pr: PR Workflow System

Canonical reference for lex-pr goals, data schema v1, gating model, and merge algorithm. Part of the SmarterGPT workflow ecosystem.

Project Goals

Parallel PR Workflows

Enable multiple PRs to be developed, tested, and merged concurrently while maintaining dependency order and preventing conflicts.

Deterministic Merge Order

Compute stable, reproducible merge sequences using topological sorting to ensure dependencies are always satisfied.

Local Gate Validation

Run comprehensive quality gates locally before merge to catch issues early and reduce CI/CD failures.

Schema v1

The plan.json schema defines the structure for PR workflow configuration and execution.

Core Fields

{ "version": "1.0.0", // Schema version identifier "items": [ // Array of PR workflow items { "id": "string", // Unique identifier for the PR "branch": "string", // Git branch name "depends_on": [], // Array of PR IDs this depends on "gates": {}, // Gate execution configuration "metadata": {} // Additional context and information } ] }

Item Fields

id: Unique string identifier for each PR item (required)

branch: Git branch name for the PR (required)

depends_on: Array of PR IDs that must be merged before this one (optional, default: [])

gates: Object containing gate execution results and configuration (optional)

metadata: Object for additional metadata like PR number, title, author (optional)

Validation Rules

• All id values must be unique within a plan

• All depends_on references must point to existing IDs in the same plan

• Dependency graph must be acyclic (no circular dependencies)

• Schema version must match supported versions (currently v1.0.0)

• Branch names must be valid Git ref names

Gating Model

Gates are quality checks that run locally before merge to ensure code quality and correctness.

Lint Gate

Purpose: Code style and quality validation

Implementation: Runs configured linters (ESLint, Prettier, etc.)

Timeout: Configurable, default 60s

Exit criteria: Zero linting errors

Typecheck Gate

Purpose: Static type validation

Implementation: TypeScript compiler in check mode

Timeout: Configurable, default 120s

Exit criteria: Zero type errors

Test Gate

Purpose: Unit and integration test execution

Implementation: Test runner (Vitest, Jest, etc.)

Timeout: Configurable, default 300s

Exit criteria: All tests passing

Gate Execution Flow

1. Parse plan.json and validate schema 2. For each PR item in topological order: a. Checkout the branch b. Run configured gates in parallel c. Capture stdout/stderr and exit codes d. Store results in gates object e. If any gate fails, halt execution 3. Generate gate execution report 4. Return success only if all gates pass

Gate Results Structure

{ "gates": { "lint": { "status": "passed" | "failed" | "skipped", "duration_ms": 1234, "exit_code": 0, "output": "string" }, "typecheck": { /* same structure */ }, "test": { /* same structure */ } } }

Merge Algorithm

The merge algorithm computes deterministic merge order using topological sorting with Kahn's algorithm.

High-Level Steps

1. Parse and Validate • Load plan.json and validate schema • Build dependency graph from items • Detect cycles and unknown dependencies • Fail fast on validation errors 2. Compute In-Degree • For each node, count incoming edges • Nodes with in-degree 0 have no dependencies • Track in-degree for each item 3. Initialize Queue • Add all items with in-degree 0 to queue • Sort queue alphabetically for determinism • Queue represents items ready to merge 4. Topological Sort (Kahn's Algorithm) • While queue is not empty: a. Remove item from queue (front) b. Add to merge order (output) c. For each dependent of current item: - Decrement its in-degree - If in-degree reaches 0, add to queue d. Sort queue for determinism 5. Validate Completeness • If output contains all items: success • Otherwise: cycle detected, fail with error • Return ordered merge levels

Merge Levels

The algorithm groups items into levels where all items in a level can be merged in parallel:

{ "levels": [ ["feat-a", "feat-b"], // Level 0: No dependencies ["feat-c"], // Level 1: Depends on Level 0 ["feat-d", "feat-e"] // Level 2: Depends on Level 1 ] }

Items within the same level have no interdependencies and can be processed concurrently.

Merge Strategies

Fast-forward: Used when target branch is direct ancestor. Preserves commit history.

Squash: Combines all commits into one. Used for clean history when appropriate.

Merge commit: Creates explicit merge commit. Used when preserving branch history is important.

Strategy selection: Configurable per item or globally. Fast-forward preferred when possible for clean history.
