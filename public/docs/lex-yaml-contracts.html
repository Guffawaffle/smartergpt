Lex contract surface

lex.yaml names what work means in this repository.

Lex stores memory and policy context. lex.yaml adds a small workflow vocabulary so agents and runners can understand the kinds of work this repo supports.

It is a contract, not an execution engine. Runners can consume it, but runner-private plan formats and orchestration details stay outside this file.

What belongs in lex.yaml

Workflows

Named units of work such as review, refactor, release, triage, analyze, or operate.

Inputs

Required values for a workflow: ticket IDs, PR numbers, module names, dataset IDs, or target environments.

Scope

Paths, modules, services, or domains the workflow may inspect or modify.

Policy hooks

Rules the workflow must respect, such as forbidden edges, review requirements, or escalation boundaries.

Modes

Optional posture hints such as explore, implement, review, operate, or recovery.

Metadata

Human-readable descriptions that let agents explain what they are doing and why.

Small example

workflows:
  review-pr:
    description: "Review a pull request with memory and policy context."
    inputs:
      pr_number:
        type: integer
        required: true
    scope:
      module_scope: "services/**"
    policy:
      must_pass:
        - "no-forbidden-edges"

  analyze-dataset:
    description: "Inspect a dataset and produce a cited summary."
    inputs:
      dataset_id:
        type: string
        required: true
    mode: "review"

What stays out

Runner internals

No private merge plans, queue formats, orchestration state, or contained workspace layouts.

Credentials

No secrets, tokens, PHI, customer data, or internal URLs. Existing IAM and brokers remain external.

Tool sprawl

Detailed command contracts belong in AXF capabilities. lex.yaml names work; AXF names executable capabilities.
